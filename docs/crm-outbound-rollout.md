# Reviewed WhatsApp replies

Apply `202609240002_crm_reviewed_replies.sql`. It creates no paid entitlement and sends no messages.

Trials start with zero WhatsApp allowance. Migration `202609240003_crm_trial_replies.sql` adds an operator-only grant of 10 reviewed replies and activates it only for the approved internal Veyrn Labs workspace if its trial is still active. The existing expiry, 25 AI drafts, shared ₹100 budget and usage history are preserved. No paid subscription is created. Rerunning the grant never resets consumed usage. The local per-reply cost estimate is 100 paise; this is a conservative budget estimate, not a Meta billing quote.

Server setup requires `WHATSAPP_SEND_ENABLED=true`, `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_SEND_ORGANIZATION_ID`, `WHATSAPP_SEND_PHONE_ID`, `WHATSAPP_SEND_WABA_ID` and a conservative positive `WHATSAPP_REPLY_COST_PAISE`. The global token is deliberately restricted to one exact organization/phone/WABA tuple. Other businesses cannot use it. Customer onboarding still requires encrypted per-tenant credentials and token lifecycle management.

An authorized member edits a current reviewable draft, checks the approval box, then presses Send WhatsApp reply. Changing text clears approval. The server derives the recipient from the conversation, checks tenant/lead access, connection, latest source message, reply window (one minute of dispatch headroom), previous opt-out wording, and messaging/cost allowance. It records the approved text, actor and usage reservation before one Meta call. AI pause controls generation; it does not prohibit an authorized human from sending an already-reviewed reply.

Each draft permits one dispatch attempt, including across multiple tabs and repeated requests. Accepted means Meta returned a message ID, not that the recipient received it. Recent outgoing history shows the last 20 attempts. Delivery/read processing is implemented by `202609240004_crm_delivery_receipts.sql`. Signed receipt events are scoped to the connection, WABA, message ID and recipient. Early receipts are retained; duplicate and out-of-order events cannot regress read/delivered status. Refresh reply history to see receipts. Old receipts already acknowledged before this deployment are not automatically recovered. No templates, campaigns or automated sending are enabled.

Explicit Meta 4xx errors with an API error code are recorded as rejected and cancel their usage reservation. Network errors, timeouts, invalid responses and 5xx responses are unknown, retain reservations, and never auto-retry. A crash between reservation and HTTP dispatch remains pending for operator reconciliation. Do not reset/delete attempts or blindly resend. A future operator workflow must reconcile provider receipts and costs before permitting retries; that workflow is not implemented here.

Accepted replies settle at the configured per-reply cost estimate, not a claim of exact Meta billing. Review against actual invoices and reconcile discrepancies. No live messages are sent by offline tests. English stop/unsubscribe/opt-out history blocks sending until an operator reviews consent; multilingual consent handling and a full consent management UI remain future work. For launch, complete durable reconciliation, per-tenant credentials and consent management. Automatic replies remain disabled: the current trial authorizes only manually approved sends. An automatic worker still needs explicit opt-in, durable jobs, knowledge/version checks, human escalation, consent checks and separate activation after receipt verification.
