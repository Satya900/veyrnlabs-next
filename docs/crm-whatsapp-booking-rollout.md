# AI-driven WhatsApp booking: first release

Apply `202609240010_crm_auto_booking.sql` after the calendar and auto-replies migrations. The
migration activates nothing on its own; it only adds columns and functions used by the opt-in
automatic-reply worker.

## Design: tiered, not autonomous booking

The model (`src/lib/crm/ai-provider.ts`) never books anything itself. Its structured output gained
one new field, `booking_request: { requested, date, time }`, alongside the existing `reply`,
`needs_human` and `reason`. The model only fills in `date`/`time` when the customer stated or
clearly implied one specific date and time; everything else is deterministic, server-side code:

- A clean request (unambiguous date/time, on the 30-minute business-hours grid, strictly in the
  future) against a real free slot is booked automatically and the customer gets a deterministic
  confirmation message, generated by the worker, not the model, so the confirmation text can never
  be a hallucination.
- Anything else, an ambiguous or missing date/time, a slot outside business hours or off the
  30-minute grid, a slot that turns out to be busy, no assigned agent, no connected calendar, or
  no active Pro Plus subscription, forces `needs_human`, exactly like the existing needs_human
  heuristics. The extracted date/time (if any) is still stored on the draft, so an agent reviewing
  it in Settings > WhatsApp sees a "Book this visit" button pre-filled with the requested slot
  instead of having to open the lead and search a calendar grid by hand.

This mirrors the trust model already used for automatic replies themselves: a strict, deterministic
gate decides whether an action goes out unattended, not the model's own say-so.

## What changed

- `src/lib/crm/calendar-slots.ts` (new): `istDayBounds`, `slotGrid`, `overlaps` extracted from
  `ScheduleVisit.tsx` (now imports them, unchanged behavior), plus `resolveIstSlot(date, time, now)`
  which resolves an IST date/time pair to a UTC instant only when it lands exactly on a bookable
  slot and is strictly in the future; anything else returns `null` rather than guessing.
- `src/lib/crm/ai-provider.ts`: `generateAIDraft` now also sends `current_date_ist` (so the model
  can resolve "tomorrow"/"next Tuesday") and validates/sanitizes `booking_request`; a malformed
  date or time is cleared to `""` without failing the rest of the draft, but a missing or
  wrong-shaped `booking_request` object fails the whole response (it is a required schema field,
  so its absence signals a genuinely garbled response).
- `crm_ai_drafts` gained `proposed_visit_at timestamptz` and
  `booking_status text default 'none' check(in ('none','attempted','booked','unavailable','failed'))`.
  `crm_finish_ai_draft` gained a sixth, optional `proposed_at timestamptz default null` parameter;
  the existing five-argument call from the human-reviewed draft path (`/api/crm/ai`) is unchanged.
- `crm_prepare_auto_booking(job, token, start_iso, end_iso)` and
  `crm_finish_auto_booking(job, token, outcome, start_iso)` (service-role only): re-validate
  entitlement, lead ownership and calendar connection independently of anything the model claimed,
  exactly like `crm_calendar_connection_for_lead` does for the manual booking flow, and mark the
  draft `'attempted'` before any external API call so a retried worker tick cannot double-book.
- `src/lib/crm/auto-worker.ts`: after generating a draft, resolves any booking intent, attempts the
  prepare/free-busy-check/create-event/finish sequence when the heuristic needs_human check has
  not already fired, and only then calls `crm_finish_ai_draft` once with the final reply (overridden
  to the deterministic confirmation text if booked), the final `needs_human`, and the resolved
  `proposed_visit_at`.
- `AIDraft.tsx` (now takes a `leadId` prop, threaded from `WhatsApp.tsx`'s `conversation.lead_id`):
  a `needs_human` draft with a stored `proposed_visit_at` shows the proposed slot and a "Book this
  visit" button that calls the existing, already-tested `POST /api/crm/calendar/book` endpoint
  directly, no new client-side booking logic.

## Activation

No new environment variables. This layer activates automatically wherever automatic replies and a
connected calendar with an active Pro Plus subscription already coexist; there is no separate
opt-in toggle. To disable automatic booking specifically while keeping automatic replies for
everything else, the current option is disabling automatic replies for that organization or
disconnecting the calendar, either of which is the same trust boundary already exposed today. A
dedicated per-organization toggle was deliberately not added in this release, to keep the option
set small until real usage shows it is needed.

## Test coverage and limits

`npm run test:crm` covers: `booking_request` extraction, sanitization of malformed date/time, and
fallback on a missing field (`crm-ai.test.mjs`); the worker's full control flow for a clean booked
slot, a busy slot, an ambiguous request and an ineligible lead, using injected fetch and RPC mocks
(`crm-auto.test.mjs`); and `crm_prepare_auto_booking`/`crm_finish_auto_booking` directly against a
real Postgres instance, entitlement, ownership, calendar-connection checks, and that a repeated
`crm_finish_auto_booking('booked')` call is a no-op rather than a duplicate activity entry
(`crm-auto.test.mjs`). Not yet exercised against a real Google account or a real WhatsApp send;
review this document's design against a live test conversation, in Google's OAuth Testing mode and
Razorpay/WhatsApp test mode, before relying on it with a real customer.

## Deliberately out of scope

- **Editing or cancelling an automatically booked visit from WhatsApp.** The customer would need to
  message the business, and an agent handles the change in Google Calendar or the CRM directly.
- **Multi-slot negotiation.** If the requested slot is busy, this release hands off to a human
  rather than having the model or the worker propose alternative times itself.
- **A per-organization opt-out for booking specifically**, independent of automatic replies as a
  whole, as noted above.
